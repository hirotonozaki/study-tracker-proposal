01OVERVIEW

プロジェクト概要

Study Tracker は、日々の学習を「科目・時間・日付・メモ」で記録し、合計時間や科目別の内訳を ダッシュボードで振り返れる Web アプリです。React 18 / TypeScript で構築し、バックエンドに Supabase（PostgreSQL） を採用。学習記録の追加・一覧・編集・削除（CRUD）を実装しています。

これまでの HTML / CSS / WordPress による Web 制作に加えて、「データベースに繋いでデータを保存・更新する Web アプリ」を 課題発見から公開まで一人で形にした制作物です。

バックエンドSupabase（PostgreSQL / Row Level Security）
データ操作Create / Read / Update / Delete（study_records テーブル）
ホスティングVercel（公開済み・継続デプロイ）

02BACKGROUND

制作背景

プログラミングや Web の学習を続ける中で、日々の学習時間を手軽に記録し、後から振り返れる仕組みが 欲しいと感じたのが出発点です。メモやノートでは「どの分野にどれだけ時間を使えているか」が見えづらく、 自分の学習を客観的に把握できる小さなツールを、自分の手でつくろうと考えました。

あわせて、これまで中心だった HTML / CSS / WordPress の Web 制作に加えて、 「データベースに繋ぎ、データを保存・更新する Web アプリ」を一から作った経験を、 きちんと形にして示したいという狙いもありました。

数あるテーマの中で「学習記録アプリ」を選んだ理由は、題材として過不足がなかったためです。 記録の追加・取得・更新・削除（CRUD）と、合計時間・科目別といった集計が一通り必要になり、 さらに SaaS のようなダッシュボード UI も練習できます。「DB を使った Web アプリ開発」を学ぶのに ちょうどよい規模だと判断しました。

この制作で示したいこと Web 制作だけでなく、DB を扱う Web アプリの開発（CRUD・集計・可視化）を、 課題発見から設計・実装・公開まで一人で完結できること。
03PROBLEM

課題設定

「ユーザーが感じる課題」と「制作を通じて技術的に達成したいこと」の2軸で設定しました。

User — ユーザーの課題

  • 勉強した内容を、手間をかけずにさっと記録したい。
  • 「どの科目をどれだけやったか」を一目で振り返りたい。
  • 続けるうちに増える記録を、見やすく整理したい。

Technical — 技術的なゴール

  • Supabase（PostgreSQL）に対して CRUD を一通り実装する。
  • DB の行・フォーム入力・集計結果を 型で表現し、壊れにくくする。
  • データ操作（API）と画面（表示）を分け、見通しのよい設計にする。
  • 合計・科目別・日付別の集計を自前で実装し、可視化する。
04TARGET USERS

ターゲットユーザー

想定するのは、独学やスキルアップのために学習を継続している人です。学習アプリやノートはあるものの、 「科目ごとの合計を後から振り返る」ところまでは手が回らない、という層を念頭に置いています。

学

独学で学習を続ける人（例）

PERSONA — INDEPENDENT LEARNER

毎日少しずつ複数科目を勉強する。記録は続けたいが、入力が面倒だと続かない。 「今週どれだけやれたか」「どの科目が手薄か」を、開いてすぐ把握できる手軽さを求めている。

入力項目を「科目・時間・日付・メモ」の最小限に絞り、開いた最初の画面で合計と科目別の内訳が見えることを、 設計の優先事項にしています。

05SOLUTION

解決方法

課題に対して、機能と画面で次のように応えました。

課題アプリでの解決
手間なく記録したい科目・時間（分）・日付・メモだけの最小フォーム。日付は当日を初期値に。
科目ごとの偏りを振り返りたいダッシュボードに科目別の合計時間を横棒バーで表示。
増える記録を整理したい記録を日付別にグループ化して一覧表示。
間違えても直したい各記録をその場で編集・削除（CRUD）。削除は確認ダイアログ付き。
全体の進み具合を知りたい合計時間・記録数・科目数・学習日数を統計カードで集計表示。

10DATABASE

データベース設計

学習記録は「ある日・ある科目を何分やったか」が 1 件の情報。これを study_records テーブル 1 つで表現しました。

study_recordsTABLE
idPKuuid主キー（gen_random_uuid()）
subjecttext科目名（not null）
minutesinteger学習時間・分（check > 0）
studied_ondate学習日（default 当日）
memotextメモ（任意・null 可）
created_attimestamptz作成日時（default now()）

設計上の判断

時間は分（integer）で保持「1.5 時間」のような小数を持たず、整数で扱うことで計算・集計が単純に。表示時に「1h 30m」へ整形。
科目はテーブルを分けない規模が小さく、科目別集計は subject でのグループ化で足りるため非正規化。正規化は今後の改善案（17 章）。
集計はアプリ側で算出合計／科目別／日付別を utils.ts の純粋関数で計算し、ダッシュボードに渡す。
インデックス並び替え・集計でよく使う studied_on（降順）と subject に付与。
本番化メモ — RLS と認証について 現在はログイン無しの単一ユーザー想定のデモのため、Row Level Security を有効化したうえで anon に CRUD を許可しています。実運用では Supabase Auth を導入し、user_id 列を追加して 「auth.uid() = user_id の行だけ操作可」へ置き換える前提です（17 章）。 今回は「DB に繋いで CRUD する」ことを示すため、あえてシンプルにしています。
11CRUD

CRUD 実装内容

Supabase への読み書きは api.ts に集約し、画面からは関数を呼ぶだけ（SQL を意識しない）構成です。 取得後はカスタムフック useStudyRecords がローカル state を持ち、操作のたびに全件を取り直さず 該当分だけ更新して即時反映します。

操作関数（api.ts）画面への反映
CreatecreateRecord()返ってきた 1 件を一覧の先頭に追加。
ReadfetchRecords()学習日の新しい順で取得し、state を初期化。
UpdateupdateRecord(id)該当 id の 1 件を差し替え。
DeletedeleteRecord(id)該当 id を state から除外。

追加（Create）の流れ

  1. フォームに入力して送信する。
  2. 入力をバリデーション（科目が空でないか／時間が 1 以上か）。
  3. api.ts の createRecord() が Supabase に insert する。
  4. 返ってきた 1 件をローカル state の先頭に追加して即時反映（再取得しない）。
  5. 失敗時は try / catch でエラーメッセージを表示する。
// api.ts — Create（追加）
export async function createRecord(input: StudyRecordInput): Promise<StudyRecord> {
  const { data, error } = await supabase
    .from('study_records')
    .insert({
      subject: input.subject,
      minutes: input.minutes,
      studied_on: input.studied_on,
      memo: input.memo.trim() === '' ? null : input.memo,
    })
    .select()
    .single();

  if (error) throw error;
  return data;
}
12WHY SUPABASE

Supabase 採用理由

DATABASE
PostgreSQL をすぐ使える

サーバーを自前で立てずに、本格的なリレーショナル DB を最初から使える。学習用途でも実務に近い形を体験できる。

CLIENT
JS から CRUD が書きやすい

@supabase/supabase-js で insert / select / update / delete を素直に記述でき、フロント側の実装に集中できる。

SECURITY
RLS と認証の道筋がある

Row Level Security と Supabase Auth が用意されており、デモ → 本番（ユーザー別データ）への発展経路が明確。

OPS
運用がシンプル

管理するサーバーがなく、個人で「設計 → 実装 → 公開」まで完結させやすい。

HTTPS

HTTPS で即時公開でき、ポートフォリオとして URL を共有しやすい。

14HIGHLIGHTS

工夫した点

工夫内容
データ操作の分離Supabase 呼び出しを api.ts に閉じ込め、状態同期を useStudyRecords に集約。画面は「表示」に専念し、後から機能を足しても壊れにくい構成に。
型で壊れにくくDB の行（StudyRecord）・フォーム入力（StudyRecordInput）・集計結果を、それぞれ別の型として定義。
集計を純粋関数に科目別・日付別・合計の集計を utils.ts の純粋関数として切り出し、見通しよく・テストしやすく。
CRUD 後の即時反映操作のたびに全件を再取得せず、返り値や id を使ってローカル state だけ更新し、体感を軽くした。
入力・状態のケア科目必須・時間 1 以上のバリデーション、読み込み中／エラー表示、削除前の確認ダイアログを用意。
15CHALLENGES

苦労した点

つまずき解決方法
環境変数と接続URL / anon key が未設定だと動かず最初につまずいた。→ クライアント生成時に未設定を検知し、原因が分かるエラーを出すようにした。
RLS で操作できないRLS を有効化したら最初は読み書きできなかった。→ 仕組みを理解し、デモ用に anon を許可するポリシーを設定（本番は Auth 前提と整理）。
状態の同期更新・削除のたびに全件再取得すると重い。→ 返り値や id を使い、ローカル state だけを更新する形にした。
